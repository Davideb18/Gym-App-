===============================================================================
| 2. DECISIONI ARCHITETTURALI & LOGICHE FONDAMENTALI                          |
===============================================================================

[A] DOPPIO FILE `.env` (Frontend vs Backend)
- PERCHÉ SONO SEPARATI: Il progetto gestisce due ambienti di sicurezza diversi.
  Il `.env` del frontend contiene chiavi pubbliche (`EXPO_PUBLIC_SUPABASE_ANON_KEY`) e DEVE poter
  essere compilato nell'APK o nell'IPA da distribuire.
  Il `.env` del backend contiene URL di bypass admin e chiavi `SERVICE_ROLE` o secret.
  Unire i due file porterebbe al rischio altissimo di esportare chiavi di amministrazione nell'app client degli utenti.
  
[B] ARCHITETTURA SERVERLESS (Supabase BaaS)
- Abbiamo eliminato il file "client.ts" che puntava a localhost:3001. Il fetching di dati
  non passa più da un API gateway custom express perché Supabase ci fornisce già un'interfaccia 
  GraphQL diretta estremamente preformante (in `frontend/src/api`).
  Il server (`backend`) servirà unicamente per operazioni pesanti off-load (Script di analisi, ML, webhooks).

[C] TIPI CONDIVISI `shared/types.ts`
- Le interfacce (Es. `Exercise`, `WorkoutTemplate`, `PlannedSet`) si trovano nella root `/shared`
  poiché sia il DB e l'interfaccia UI, che i futuri calcoli backend, devono usare la medesima modellazione dati
  per evitare bug di desincronizzazione.
